# Backend credential-exchange contract

## Goal

A Home Assistant user should enter only the share code produced by 86Proof.
They should never need Firebase Console access, an Apple sign-in flow, an
email/password Firebase account, or a service-account key.

The Home Assistant integration needs a normal Firebase Auth viewer identity so
that existing Firestore rules continue to govern every inventory read.

## Callable Function

The Gen 2 Firebase callable `authorizeHomeAssistant` is deployed in
`us-central1`.

A dependency-injected implementation and its dependency-free unit tests live
in [`backend/functions`](../backend/functions). In the existing 86Proof
`functions/index.js`, register it after Firebase Admin has been initialized:

```js
const { getAuth } = require("firebase-admin/auth");
const {
  createAuthorizeHomeAssistant,
} = require("./authorize-home-assistant");

exports.authorizeHomeAssistant = createAuthorizeHomeAssistant({
  onCall,
  HttpsError,
  db,
  auth: getAuth(),
  FieldValue,
});
```

Copy `authorize-home-assistant.js` beside the existing `index.js` first. The
module uses only dependencies already present in the 86Proof Functions
package.

The Function writes hashed counters to `_proof86_rate_limits`. Configure
Firestore TTL on that collection's `expiresAt` field so stale counters are
removed automatically. The collection has no client-access rule and remains
server-only.

### Request

The initial request is unauthenticated and uses the standard Firebase callable
envelope:

```http
POST https://us-central1-proof-43495.cloudfunctions.net/authorizeHomeAssistant
Content-Type: application/json

{
  "data": {
    "inviteCode": "ABCDEFGH",
    "installationId": "a locally generated UUID",
    "displayName": "Home Assistant",
    "expectedBarId": "optional existing bar ID during reauthentication"
  }
}
```

`installationId` is a random identifier generated by the Home Assistant config
flow. It is not a hardware identifier and contains no user information.

### Successful response

```json
{
  "result": {
    "barId": "shared bar document ID",
    "barName": "Joshua's Bar",
    "viewerUid": "Firebase Auth UID created for this installation",
    "customToken": "short-lived Firebase custom token"
  }
}
```

The integration immediately exchanges `customToken` through Firebase Auth's
`accounts:signInWithCustomToken` endpoint. It persists only the resulting
refresh token and identifying metadata.

## Required server behavior

The Function should:

1. Normalize and validate the eight-character invite code.
2. Apply per-IP and per-code rate limits before querying Firestore.
3. Find exactly one active `shared_bars` document with that invite code.
4. Enforce any subscription or sharing eligibility required by 86Proof.
5. If `expectedBarId` is present, reject the request unless it matches the
   resolved bar. This check must happen before creating a member or Auth user.
6. Create or reuse a Firebase Auth identity tied to the combination of bar and
   installation ID.
7. Create or restore that identity's `viewer` member document.
8. Mint a short-lived Firebase custom token for the viewer UID.
9. Return only the fields in the successful response above.

Retries with the same bar and installation ID must be idempotent. A share code
for a different bar must not be allowed to silently move an existing viewer
identity.

## Revocation

The viewer appears in the existing shared-bar member list. Removing it deletes
the member document, after which Firestore bottle reads return
`PERMISSION_DENIED`. The integration converts that response into Home
Assistant's standard reauthentication flow.

Re-entering a valid share code during reauthentication calls the same Function
with the existing installation ID and restores or replaces the credential.

## Security requirements

- Never return a service-account credential.
- Never let the Function return arbitrary bar data before membership is
  established.
- Do not log invite codes, custom tokens, ID tokens, or refresh tokens.
- Use constant-shape errors for unknown, expired, and inactive invite codes.
- Add abuse monitoring and conservative quotas before public release.
- Keep inventory writes owner-only; this authorization flow creates viewers.
- Rotate an invite code without invalidating existing viewers.

## Callable errors consumed by the integration

| Callable status | Home Assistant result |
|---|---|
| `invalid-argument`, `not-found`, `failed-precondition` | Invalid share code |
| `resource-exhausted` | Rate limited / cannot connect |
| `unauthenticated`, `permission-denied` | Invalid authorization |
| Other or unavailable | Cannot connect |
